chpl-screenshots · later generation · simplified architecture · 2026-07

A frontier agent investigates screen clusters and writes tested extractors. The live path runs them locally.

Frequent screenshots and optional timestamped signals produce a growing catalog of repeated screen patterns. A frontier agent browses that catalog, chooses clusters to investigate, sends selected screenshots to an image annotation model, writes deterministic route code, and tests it against the remaining examples. Promoted routes extract useful states or ignore known irrelevant states.

§ 00

Two operating planes

The live data plane records, fingerprints, matches, extracts, ignores, and clusters. It runs locally with deterministic code. The agent compilation plane studies accumulated clusters and produces new route code.

Live data planeLooks up each candidate packet in the local state registry. A matched route extracts or ignores. Unknown and ambiguous packets join the cluster catalog.
Cluster catalogGroups similar unknown packets, tracks recurrence, and exposes representative screenshots and transitions for browsing. Hashes organize evidence but carry no semantic label.
Agent compilation planeA frontier agent chooses investigations, calls an image annotation model, writes route code, runs holdouts, diagnoses failures, and promotes tested routes.

Promotion is the only path from agent work into the live registry. Runtime exceptions, drift cases, and random audit samples travel in the other direction as new compilation evidence.

Unknown packets do not trigger model calls. They increase cluster counts and improve the representative sample. The frontier agent spends a separate investigation budget over the catalog.

Repository evidence used here

evidence{value, box} supports inspection.

The current viewer links extracted values to pixels. Evidence packets extend the same link across a timestamped screenshot sequence.

schemaSmall targets performed better.

The flat patientId target captured more values than the nested identifier experiment. Each compile target starts with a bounded product question.

operationsLedgers make failures countable.

Per-vendor shards, attempt records, resumability, and click-through reports kept zero-yield work visible. Cluster, route, and runtime ledgers use the same pattern.

§ 01

Agent compilation loop

The agent works on clusters rather than individual live packets. Its tools list clusters by recurrence, age, visual diversity, and current route status. The agent can open representative screenshots and nearby transitions before deciding whether to spend annotation or coding effort.

01 · BROWSE

Cluster selection

Review cluster counts, representative contact sheets, transition context, and current coverage. Choose an investigation based on expected value and information gain.

02 · INSPECT

Example review

Open a few diverse examples. Decide whether the cluster is coherent, relevant to the product question, irrelevant, or in need of more evidence.

03 · ANNOTATE

Targeted image reading

Send selected screenshots to an image model for structured values, text, and bounding boxes. Request more examples only when the current hypothesis needs them.

04 · WRITE

Route implementation

Write deterministic matching code and either an extractor or ignore action. Use pixels and any available optional timestamped signals.

05 · TEST

Holdout execution

Run the candidate route over the rest of the cluster plus similar negative clusters. Inspect misses, collisions, validator failures, and output distributions.

06 · REVISE

Repair or promote

Use failures to choose the next annotation or code change. Promotion requires labeled holdouts and the full regression suite.

Example investigation

A new cluster contains 50 visually similar packets. The agent views a contact sheet, opens several representatives, and sends three diverse screenshots to the image annotation model. Those annotations include the target fields and their boxes. The agent writes a candidate matcher and extractor, then runs it over the other 47 packets and nearby negative clusters.

The 47 packets provide a behavioral holdout: they reveal match coverage, crashes, unstable outputs, and validator failures. They do not become an accuracy set until they have independent labels. The agent therefore sends a random subset and any suspicious cases for annotation, then revises the route. Native DOM or accessibility text can label additional cases when available.

An irrelevant cluster follows the same process but produces an ignore route. Future matches are counted and a random sample returns for audit.

Live route lookup

Every promoted route contains a deterministic matcher tested against positive packets and similar negative packets. A local index narrows the registry before the route matchers run:

fingerprint = localFingerprint(packet)
candidates  = registry.shortlist(fingerprint, availableSignals)
routes      = candidates.filter(route => route.matches(packet))

if routes.length !== 1: return clusters.add(packet)
if routes[0].action === "ignore": return audits.maybeSample(packet)
return routes[0].extractAndValidate(packet)

The pixels-only fingerprint can include screen dimensions, perceptual hashes over stable regions, and OCR anchor tokens. Process and window identity, DOM structure, accessibility roles, and recent input events narrow the shortlist when available. Dynamic values such as patient name and MRN stay out of the stable signature. Zero matches and tied matches enter the cluster catalog.

Product questions define relevant states

Examples

  • a patient identity banner becomes visible or changes
  • an order is prepared, signed, or acknowledged
  • a medication or result list reaches a readable state
  • a workflow milestone appears on screen

Scope

  • start with one question and its output schema
  • collect positive, negative, and ambiguous packets
  • include matches() and an explicit action in every route
  • extend shared state infrastructure in response to measured failures
Investigation scheduling. The agent chooses work from recurrence, product value, novelty, and expected information gain. A separate random allocation samples low-ranked clusters so the priority function cannot hide systematic misses.

Generated code contract

The first implementation permits ordinary TypeScript inside the route interface. A generated route can use DOM selectors, accessibility queries, OCR over stable regions, label/value parsing, input-event sequences, or a small composition of these techniques.

Generated code runs in a sandbox with pinned dependencies, bounded resources, disabled ambient network access, and explicit input/output contracts. Held-out and regression tests control promotion.

Repeated implementation patterns can move into shared libraries after several successful routes establish the common interface.

§ 03

Input availability

Frequent screenshots form the baseline input. “Optional timestamped signals” means separately captured DOM, accessibility, process, window, click, and type streams aligned to the screenshot clock. Any of these streams may be missing. Each route manifest lists the signals it can use and the signals it requires.

SignalContributionOrdinary desktopOpaque Citrix / VDI
Frequent screenshotsCanonical visual record: layout, visible text, transitions, occlusion, and the only universally available evidence.requiredrequired

Type streamBurst timing, focus/target hints, and optional text where policy explicitly allows it. Raw typed text is not required.usuallytiming only
DOM snapshotsExact text, element roles, geometry, and stable application identifiers for browser surfaces.sometimesnormally absent
Accessibility treeNative text, controls, roles, and bounding rectangles without OCR.sometimesnormally absent

Citrix constraint. Pixels-only capture must support the complete path from packet creation through state matching and extraction. Rich desktop signals can improve speed and accuracy. When both forms are available during development, native text supplies labels for pixels-only route tests.

Capture policy stays separate from extraction logic

“Always-on” means the system continuously produces the screenshot stream while it is enabled. Frequency, resolution, chunking, encryption, access, and retention are deployment policies. Because these streams can contain PHI and credentials, recording requires explicit authorization, strong tenant isolation, audited access, and a clear deletion policy. Route code should consume packet references without gaining broader access to the archive.

§ 04

Evaluation, drift, and repair

Image-model annotations seed the labeled corpus but do not provide independent ground truth. Evaluation combines deterministic checks, agent-scheduled annotation audits, independent data sources, and human adjudication. This mix covers route drift as well as errors shared by the annotation model and route code.

PASSEmit with provenance; retain metrics; sample some clean cases.
ABSTAINSuppress the output and add the packet to the route’s exception cluster.
DISAGREEStore both results for the agent to inspect and target for annotation.
NOVELAdd the packet to the unknown cluster catalog and update group counts.
DRIFTDisable or narrow the route and send its new cases back to the workbench.

Automated feedback

  • deterministic grammars, ranges, cross-field invariants, and temporal consistency
  • agent-scheduled image annotations on random and risk-weighted runtime samples
  • oversampling of new routes, ignore routes, pixels-only routes, and thin validator margins
  • automatic replay of every route on its full regression corpus

Independent evidence

  • DOM or accessibility text when it exposes the application’s actual value
  • synthetic/test environments whose database contains the expected value
  • workflow outcomes and cross-time invariants that reveal impossible changes
  • authorized human adjudication for consequential or persistent ambiguity
Regression policy. Every resolved exception becomes a permanent fixture. A repair request includes the failing packet, old code, expected result, and test history. The revised route must pass the full corpus. Repeated failures trigger a review of the matcher boundary and extraction approach.

Operational metrics

Route coverageshare of candidate packets with exactly one promoted extract or ignore route
Unknown catalogpacket rate, cluster count, recurrence distribution, and time waiting for investigation
Extraction accuracyfield scores against independently labeled holdouts, split by route, version, and available signals
False-ignore raterelevant states found in random audits of packets handled by ignore routes
Compilation efficiencyagent work, image annotations, elapsed time, and cost per promoted route
Runtime performancep50/p95 latency, abstentions, ambiguous matches, route disables, and repeat exceptions

Reporting rules

  1. Use “accuracy” only for comparisons against an independent label. Annotation/route comparison reports agreement.
  2. Audit a random slice of clean outputs in addition to cases flagged by guards.
  3. Retain negative, missed, abstained, and failed packets in evaluation datasets.
  4. Version the question, schema, model, prompt, packet format, code, fixtures, and metrics together.
  5. Make every aggregate clickable back to the packets and decisions behind it, as the current viewer does.
§ 05

Implementation sequence

The first implementation proves that an agent can discover a recurring cluster, commission annotations, write a route, test it, and install it in the local registry.

phase 0

Capture + replay

Capture frequent screenshots in timestamped chunks and align available DOM, accessibility, process, window, click, and type streams. Build a replay view over the combined timeline.

EXIT · an investigator can reconstruct a session and create a stable evidence packet
phase 1

Cluster catalog

Fingerprint candidate packets, group similar unknowns, track counts, retain diverse representatives, and expose a browser for clusters and their examples.

EXIT · repeated states appear as browseable groups while random review quantifies cluster errors
phase 2

Agent workbench

Give a frontier agent tools to list clusters, view examples and transitions, request structured image annotations, edit route code, execute it in a sandbox, and inspect holdout reports.

EXIT · the agent can complete a browse, annotate, write, test, revise cycle without manual file plumbing
phase 3

First compiled routes

Start with one recurring relevant cluster and one recurring irrelevant cluster. Build an extract route and an ignore route, each tested against similar negative states and labeled holdouts.

EXIT · both routes pass promotion policy and install into the local state registry
phase 4

Shadow runtime

Run promoted routes over new packets, record every decision, sample extract and ignore actions for audit, and send exceptions back to the workbench.

EXIT · route coverage and labeled accuracy hold under new screenshot streams, including pixels-only samples
phase 5

Continuous compilation

Schedule agent investigations by recurrence, product value, novelty, and information gain. Recompile routes from runtime failures and drift cases.

EXIT · route coverage rises, unknown recurrence falls, and repeat exceptions decline

Required decisions

  • the first product question and its small output schema
  • screenshot frequency, packet format, clock, and replay contract
  • cluster browser and frontier-agent tool contracts
  • image annotation schema, route sandbox, and test harness
  • promotion, audit, rollback, retention, and review policy

Deferred design

  • a universal clinical activity taxonomy
  • a global screen-family and layout-variant hierarchy
  • a bespoke route DSL or cross-site registry
  • exact hashing, clustering, OCR, or settle algorithms
  • a multi-tier local-model serving ladder
Success criteria. Promoted route coverage rises, recurring unknown clusters decline, and labeled extraction quality holds or improves. Rising false-ignore rates, rising audit disagreement, or repeated exceptions block further promotion.
